# JJC-20260320-002 · 六部通讯优化清单

## 一、目标
在皇上主仓 `origin=https://github.com/yuanshi2016/edict.git` 基线之上，继续优化六部之间的通讯协同链路，重点收敛：
1. 职责路由
2. 消息模板
3. 取证边界
4. 记忆提案收敛口径

---

## 二、当前已解决的问题
### 1. 六部职责路由已明确
已固化口径：
- 工部 = 开发 / 架构 / 代码
- 兵部 = 基础设施 / 部署 / 安全
- 户部 = 数据分析 / 报表 / 成本
- 礼部 = 文档 / UI / 对外沟通
- 刑部 = 审查 / 测试 / 合规
- 吏部 = 人事 / Agent 管理 / 培训

### 2. 六部统一回奏模板已补齐
六部 `AGENTS.md` 现已明确：
- 回奏必须包含：`任务ID / 结果 / 证据/文件路径 / 阻塞项 / 建议记忆项`

### 3. 跨会话取证边界已补齐
六部 `AGENTS.md` 已明确：
- 若使用跨会话取证，必须记录：
  - `Purpose`
  - `Minimum Scope`
  - `Maximum Range`
  - `SessionKey`
  - `Timestamp`
  - `Quoted Summary`
  - `Follow-up`
- 明确禁止无边界扫全量历史

### 4. 记忆提案收敛口径已补齐
六部 `AGENTS.md` 已明确：
- 本部只写本部 `memory/meta/pending-memories.md`
- 执行经验 / 阻塞 / 职责边界必须形成提案
- 尚书省负责汇总六部执行经验
- 中书省周度收敛，太子月度抽检

### 5. 尚书省派发模板已补齐
尚书省 `SOUL.md` 现已新增：
- 尚书省 → 六部任务令模板
- 六部 → 尚书省回奏模板
- 跨会话取证边界模板
- 记忆提案收敛口径

这意味着：
- 尚书省的派发消息不再只是“任务 + 输出要求”的简口径
- 而是有了**职责边界 / 取证要求 / 记忆要求 / 截止节点**的完整模板

## 四、仍需优化的问题（非泛泛观察，而是具体剩余项）
### 1. 尚书省尚未用新模板跑一轮六部真实闭环
这是当前最主要的剩余项。

现在协议和模板都已补齐，但还缺：
- 尚书省按新模板向六部发 1 轮真实任务令
- 六部按新模板完整回奏
- 尚书省按新模板完成汇总
- 中书省核验六部字段完整性、证据质量、记忆提案质量

### 2. 尚无统一质量扫描脚本
当前通讯协议已经统一，但还缺一个固定检查脚本，自动扫：
- 是否缺 `任务ID / 结果 / 证据/文件路径 / 阻塞项 / 建议记忆项`
- 是否存在空泛提案
- 是否存在缺 `SessionKey + Timestamp` 的取证记录

这不是当前阻塞，但属于下一步应补的增强项。

### 3. 多部门依赖回路尚未模板化
目前已明确“不得跨部直连，需经尚书省转派”，但仍可进一步优化：
- 当工部需要刑部测试、礼部文案配合时，统一回“请尚书省转派至 X 部”
- 可后续补一个更短的依赖转派模板，减少自由发挥

## 五、建议下一步
### 第一步（最优先）
由尚书省按新模板发起 **1 轮六部真实闭环试跑**。
- 执行侧建议最小入口：**工部主承接 + 刑部协同审查** 的低风险双部门闭环
- 且应刻意覆盖一次“**请尚书省转派至 X 部**”依赖分支，验证不得跨部直连的回路

### 第二步
由中书省按统一标准核验：
- 字段是否完整
- 证据是否可落地
- 取证边界是否合规
- 记忆提案是否不空泛、不越权

### 第三步
补一个统一质量扫描脚本，作为增强项，后续纳入六部常态化运行。
