# api_design

在需要设计或评审 API 时使用本技能。

## 适用场景

- 新增 RESTful API / RPC API
- 对已有接口做重构或统一规范
- 设计鉴权、分页、过滤、幂等、错误码
- 评审接口是否易用、稳定、可扩展

## 设计流程

1. 明确业务目标
   - 谁会调用
   - 要解决什么问题
   - 核心资源是什么
2. 定义资源模型
   - 资源名称
   - 主键 / 唯一键
   - 字段约束
   - 状态流转
3. 设计接口
   - 路径
   - 方法（GET / POST / PUT / PATCH / DELETE）
   - 请求参数
   - 返回结构
4. 定义错误处理
   - 4xx 与 5xx 边界
   - 统一错误码 / 错误信息
   - 可重试 / 不可重试
5. 设计非功能特性
   - 鉴权与权限控制
   - 限流
   - 幂等键
   - 分页 / 排序 / 过滤
   - 版本兼容
6. 落地建议
   - 数据库表设计建议
   - 测试点
   - 监控与日志字段

## 输出格式

### API 目标
- 用 2~4 句话说明用途和边界

### 资源模型
- 列出主要对象与关键字段

### 接口清单
每个接口包含：
- 方法 + 路径
- 用途
- 请求字段
- 返回字段
- 错误情况

### 关键设计决策
- 为什么这样命名
- 为什么选这个状态机/分页方案/鉴权方式

### 风险与建议
- 兼容性风险
- 安全风险
- 性能风险
- 运维建议

## 守则

- 优先清晰一致，不要炫技
- 避免“一个接口做所有事”
- 尽量让错误返回可读、可定位
- 如果需求本身含糊，先补出假设再设计
